## Part 2: Multi-Cloud Refactor Plan - Minimizing Duplication

### Key Principle: **Provider-Specific Resources, Shared Logic**

**What should be provider-specific:**
- Terraform modules (AWS ECS vs GCP Cloud Run are fundamentally different)
- Provider backends (S3 vs GCS)
- Provider authentication
- Container orchestration logic (ECS vs Cloud Run)

**What can be shared:**
- Deployment workflow orchestration
- Database setup/initialization logic
- Frontend build/deployment patterns
- Testing/verification logic
- Environment variable management
- Common deployment phases

#### 3. Unified Orchestrator

**Create:** `run_scripts/main_application_scripts/run.sh` (unified entry point)

```bash
#!/bin/bash
# Unified deployment orchestrator
# Usage: run.sh deploy <provider> --container-type <container> <env> [options]

SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
REPO_ROOT="${REPO_ROOT:-$(cd "$SCRIPT_DIR/../.." && pwd)}"

source "$REPO_ROOT/run_scripts/shared/logger.sh"
source "$REPO_ROOT/run_scripts/main_application_scripts/common/provider-abstraction.sh"

# Parse arguments
PROVIDER="${1:-aws}"  # Default to aws for backward compatibility
shift

# Validate provider
case "$PROVIDER" in
    aws|gcp)
        ;;
    *)
        log_error "Invalid provider: $PROVIDER (must be aws or gcp)"
        exit 1
        ;;
esac

# Route to provider-specific orchestrator (which uses common phases)
"$SCRIPT_DIR/$PROVIDER/run.sh" "$@"
```

### Duplication Analysis

#### What WILL be duplicated (acceptable):
1. **Terraform modules** - AWS ECS and GCP Cloud Run are fundamentally different
   - ✅ **Acceptable**: Provider-specific resources must be separate

2. **Provider backends** - S3 vs GCS
   - ✅ **Acceptable**: Each provider needs its own backend

3. **Container orchestration** - ECS vs Cloud Run vs GKE
   - ✅ **Acceptable**: Different APIs and concepts

#### What WON'T be duplicated (shared):
1. **Deployment workflow orchestration** - `common/container-deploy-phases.sh`
2. **Database schema initialization** - `common/database/init_schema_*.sh` (provider-specific implementations, shared interface)
3. **Data loading logic** - `common/database/load_data_*.sh` (provider-specific implementations, shared interface)
4. **Verification logic** - `common/verification/` (shared with provider-specific URL fetching)
5. **Environment variable management** - `common/env/` (shared)
6. **Prerequisites checking** - `common/prerequisites/` (already shared)

### Minimization Strategy

#### 1. Extract Common Patterns to Functions

**Example: Frontend Deployment Pattern**
```bash
# common/frontend-deploy-pattern.sh

deploy_frontend_pattern() {
    local provider="$1"
    local container_type="$2"
    local environment="$3"
    
    # Common steps:
    # 1. Build frontend (shared)
    build_frontend "$container_type" "$environment"

    # 3. Configure CDN (provider-specific)

```

### Code Duplication Metrics

#### Before Refactor:
- Deployment phases: **Duplicated** (would be in aws/run.sh and gcp/run.sh)
- Database setup: **Partially shared** (common/database/ exists)
- Verification: **Would be duplicated**
- Frontend deployment: **Would be duplicated**

#### After Refactor:
- Deployment phases: **Shared** (common/container-deploy-phases.sh)
- Database setup: **Shared interface, provider-specific implementations**
- Verification: **Shared** (common/verification/)
- Frontend deployment: **Shared pattern, provider-specific implementations**
- Terraform modules: **Provider-specific** (unavoidable - different resources)

**Estimated Duplication Reduction: ~70%**

### Implementation Phases (Minimizing Duplication)

#### Phase 1: Extract Common Logic (Before Provider Separation)

1. **Create common deployment phases:**
   - Move `aws/shared/container-deploy-common.sh` → `common/container-deploy-phases.sh`
   - Make it provider-agnostic (accept `$PROVIDER` parameter)

2. **Create provider abstraction layer:**
   - `common/provider-abstraction.sh` with helper functions

3. **Update AWS run.sh to use common phases:**
   - Test that AWS still works with shared phases

#### Phase 2: Restructure Terraform (Provider Separation)

1. Move Terraform to `providers/aws/` and `providers/gcp/`
2. Update paths in scripts using abstraction functions

#### Phase 3: Create GCP Implementation

1. Create `gcp/run.sh` using same common phases
2. Implement GCP-specific modules
3. Implement GCP-specific scripts (deploy-frontend.sh, etc.)

### Benefits of This Approach

1. ✅ **Minimal Duplication**: ~70% reduction in duplicated code
2. ✅ **Clear Separation**: Provider-specific resources stay separate
3. ✅ **Easy to Maintain**: Changes to deployment workflow affect all providers
4. ✅ **Easy to Test**: Common logic tested once
5. ✅ **Scalable**: Adding new providers requires minimal code

### Summary

**Duplication Minimization Strategy:**
1. ✅ Extract deployment phases to `common/container-deploy-phases.sh`
2. ✅ Create provider abstraction layer (`common/provider-abstraction.sh`)
3. ✅ Use shared patterns for frontend, database, verification
4. ✅ Keep provider-specific Terraform modules separate (unavoidable)
5. ✅ Keep provider-specific implementations separate (CloudFront vs Cloud CDN)

**Result:** Maximum code reuse while maintaining clear provider separation.
