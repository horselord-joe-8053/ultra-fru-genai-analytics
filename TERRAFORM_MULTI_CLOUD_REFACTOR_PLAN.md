## Part 2: Multi-Cloud Provider Refactor Plan

### Goal

Support commands like:
```bash
run.sh deploy aws --container-type ecs dev --preempt
run.sh deploy aws --container-type eks dev --preempt
run.sh deploy gcp --container-type cloud-run dev --preempt
run.sh deploy gcp --container-type gke dev --preempt
```

infra/terraform/

### Key Design Decisions

#### 1. Provider Separation at Root Level
- **Why**: Each provider has different:
  - Backend (AWS: S3, GCP: GCS)
  - Provider configuration (AWS provider vs Google provider)
  - Module implementations (AWS ECS vs GCP Cloud Run)
  - Environment variables and authentication

#### 2. Container Type Mapping
- **AWS**: `ecs`, `eks`
- **GCP**: `cloud-run`, `gke`
- **Future Azure**: `container-instances`, `aks`

#### 3. Script Structure Changes

**Current:**
```
run_scripts/main_application_scripts/
├── aws/
│   └── run.sh                    # AWS-specific
└── local/
    └── run.sh                    # Local Docker Compose
```

**Proposed:**
```
run_scripts/main_application_scripts/
├── aws/
│   └── run.sh                    # AWS orchestrator
├── gcp/
│   └── run.sh                    # GCP orchestrator (NEW)
└── common/                       # Shared deployment logic
    ├── container-deploy-common.sh
    ├── database/
    └── ...
```

**Alternative (Unified):**
```
run_scripts/main_application_scripts/
└── run.sh                        # Unified orchestrator
    # Usage: run.sh deploy <provider> --container-type <container> <env>
    # Routes to provider-specific logic
```

### Implementation Phases

#### Phase 1: Restructure Terraform (Provider Separation)

1. **Create provider directories:**
   ```bash
   mkdir -p infra/terraform/providers/aws/{modules,environments}
   mkdir -p infra/terraform/providers/gcp/{modules,environments}
   ```

2. **Move AWS modules:**
   ```bash
   mv infra/terraform/modules/* infra/terraform/providers/aws/modules/
   ```

3. **Move AWS environments:**
   ```bash
   mv infra/terraform/environments/* infra/terraform/providers/aws/environments/
   ```

4. **Update all module source paths:**
   - Change `source = "../alb"` → `source = "../alb"` (relative paths stay same within provider)
   - Update terragrunt.hcl files to point to new module locations

5. **Create GCP scaffolding:**
   - Create `infra/terraform/providers/gcp/environments/root.hcl` with GCS backend
   - Create `infra/terraform/providers/gcp/environments/dev/` structure
   - Create placeholder GCP modules

#### Phase 2: Update Scripts for Provider Parameter

1. **Update `run.sh` to accept provider:**
   ```bash
   # Current: run.sh deploy --container-type ecs dev
   # New:     run.sh deploy <provider> --container-type <container> <env>
   
   # Parse provider argument
   PROVIDER="$1"  # aws, gcp
   shift
   
   # Route to provider-specific logic
   case "$PROVIDER" in
       aws)
           "$SCRIPT_DIR/aws/run.sh" "$@"
           ;;
       gcp)
           "$SCRIPT_DIR/gcp/run.sh" "$@"
           ;;
       *)
           log_error "Invalid provider: $PROVIDER (must be aws or gcp)"
           exit 1
           ;;
   esac
   ```

2. **Update Terraform deploy scripts:**
   - Add `PROVIDER` parameter
   - Update paths: `infra/terraform/providers/$PROVIDER/environments/...`

3. **Update all script references:**
   - `TERRAFORM_DIR="$REPO_ROOT/infra/terraform/environments/$ENVIRONMENT"`
   - → `TERRAFORM_DIR="$REPO_ROOT/infra/terraform/providers/$PROVIDER/environments/$ENVIRONMENT"`

#### Phase 3: GCP Implementation

1. **Create GCP modules:**
   - `gcp/modules/cloud-run/` - Cloud Run service
   - `gcp/modules/gke/` - GKE cluster
   - `gcp/modules/cloud-sql/` - Cloud SQL PostgreSQL
   - `gcp/modules/vpc/` - GCP VPC
   - `gcp/modules/iam/` - GCP IAM
   - `gcp/modules/secret-manager/` - GCP Secret Manager
   - `gcp/modules/cloud-storage/` - GCS buckets
   - `gcp/modules/frontend/` - Cloud CDN + Cloud Storage
   - `gcp/modules/infrastructure/` - Infrastructure layer

2. **Create GCP environments:**
   - `gcp/environments/dev/` with Cloud Run and GKE configs
   - `gcp/environments/prod/` with Cloud Run and GKE configs

3. **Create GCP run.sh:**
   - Similar structure to AWS `run.sh`
   - Routes to GCP-specific deployment logic

### Migration Strategy

#### Option A: Big Bang (Recommended for Clean State)
1. Create new structure
2. Move all AWS files
3. Update all references
4. Test AWS deployments
5. Add GCP scaffolding

**Pros:**
- Clean separation from start
- No intermediate states
- Easier to understand

**Cons:**
- Large change set
- Requires careful testing

#### Option B: Gradual Migration
1. Create `providers/aws/` alongside existing structure
2. Copy (don't move) files
3. Update scripts to use new paths
4. Test thoroughly
5. Remove old structure
6. Add GCP

**Pros:**
- Safer migration
- Can rollback easily

**Cons:**
- Temporary duplication
- More complex migration

### File Path Updates Required

#### Scripts to Update:
1. `run_scripts/main_application_scripts/aws/run.sh`
2. `run_scripts/main_application_scripts/aws/terraform/deploy.sh`
3. `run_scripts/main_application_scripts/aws/terraform/teardown.sh`
4. `run_scripts/main_application_scripts/aws/shared/deploy-frontend.sh`
5. `run_scripts/main_application_scripts/aws/verification/fetch-deployment-info.sh`
6. `run_scripts/main_application_scripts/aws/verification/print-manual-hints.sh`
7. `run_scripts/main_application_scripts/aws/shared/resources_cleanup/helpers/reference-check-frontend-bucket.sh`

**Pattern to replace:**
```bash
# Old:
TERRAFORM_DIR="$REPO_ROOT/infra/terraform/environments/$ENVIRONMENT"

# New:
PROVIDER="${PROVIDER:-aws}"  # Default to aws for backward compatibility
TERRAFORM_DIR="$REPO_ROOT/infra/terraform/providers/$PROVIDER/environments/$ENVIRONMENT"
```

#### Terragrunt Files to Update:
1. All `terragrunt.hcl` files in environments
2. Module source paths (if absolute paths are used)

**Pattern:**
```hcl
# Old:
terraform {
  source = "${get_terragrunt_dir()}/../../../modules//ecs"
}

# New:
terraform {
  source = "${get_terragrunt_dir()}/../../../../providers/aws/modules//ecs"
}
```

### Backward Compatibility

**Option 1: Default Provider (Recommended)**
- If `PROVIDER` not specified, default to `aws`
- Allows existing commands to work: `run.sh deploy --container-type ecs dev`
- New commands: `run.sh deploy aws --container-type ecs dev`

**Option 2: Explicit Provider Required**
- Require provider in all commands
- More explicit, but breaks existing scripts

### Container Type Validation

**Per Provider:**
```bash
validate_container_type() {
    local provider="$1"
    local container_type="$2"
    
    case "$provider" in
        aws)
            if [[ "$container_type" != "ecs" && "$container_type" != "eks" ]]; then
                log_error "Invalid container type for AWS: $container_type (must be ecs or eks)"
                return 1
            fi
            ;;
        gcp)
            if [[ "$container_type" != "cloud-run" && "$container_type" != "gke" ]]; then
                log_error "Invalid container type for GCP: $container_type (must be cloud-run or gke)"
                return 1
            fi
            ;;
        *)
            log_error "Invalid provider: $provider"
            return 1
            ;;
    esac
    return 0
}
```

### Benefits of This Structure

1. ✅ **Clear Separation**: Each provider is self-contained
2. ✅ **Easy to Add Providers**: Just create `providers/<new-provider>/`
3. ✅ **No Cross-Provider Contamination**: AWS modules don't mix with GCP
4. ✅ **Provider-Specific Backends**: Each provider uses its native backend
5. ✅ **Scalable**: Easy to add Azure, etc.
6. ✅ **Maintainable**: Changes to one provider don't affect others

### Challenges

1. ⚠️ **Code Duplication**: Some logic (e.g., frontend deployment) may be similar across providers
   - **Solution**: Extract to `common/` if truly identical, otherwise keep provider-specific

2. ⚠️ **Migration Effort**: Large refactor affecting many files
   - **Solution**: Phased approach, thorough testing

3. ⚠️ **State Migration**: Existing Terraform state in S3
   - **Solution**: State files can stay in S3, just update paths in Terragrunt configs

### Recommended Approach

**Use Option A (Big Bang) with these steps:**

1. **Create new structure** (don't move yet)
2. **Update all scripts** to use `PROVIDER` parameter and new paths
3. **Move AWS files** to `providers/aws/`
4. **Update all Terragrunt configs** with new paths
5. **Test AWS deployments** thoroughly
6. **Add GCP scaffolding** (empty modules initially)
7. **Implement GCP modules** incrementally

### Example: Updated Command Flow

```bash
# User runs:
./run_scripts/main_application_scripts/run.sh deploy aws --container-type eks dev --preempt

# Flow:
1. run.sh parses: PROVIDER=aws, CONTAINER_TYPE=eks, ENV=dev, PREEMPT=true
2. Routes to: aws/run.sh deploy --container-type eks dev --preempt
3. aws/run.sh sets: TERRAFORM_DIR="infra/terraform/providers/aws/environments/dev"
4. Calls: terraform/deploy.sh dev eks
5. terraform/deploy.sh uses: infra/terraform/providers/aws/environments/dev/eks/
6. Terragrunt sources: infra/terraform/providers/aws/modules/eks/
```

## Summary

### Redundant Files to Remove:
- ✅ `.terragrunt-cache/` directories (can be deleted, regenerated)
- ✅ `.terraform/` directories (can be deleted, regenerated)
- ⚠️ Keep `.terraform.lock.hcl` files (should be committed)

### Refactor Plan:
1. **Restructure**: Move to `infra/terraform/providers/{aws,gcp}/`
2. **Update Scripts**: Add `PROVIDER` parameter, update paths
3. **Maintain Compatibility**: Default to `aws` if not specified
4. **Implement GCP**: Create GCP modules and environments
5. **Test Thoroughly**: Verify AWS still works, then add GCP

This structure provides a clean, scalable foundation for multi-cloud support.
